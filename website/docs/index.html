Getting started · RC5.13

Your first collection.

Kitrove collects skills from your agent tools and helps you apply compatible capabilities elsewhere. You choose what to adopt, where to put it, and which changes to approve.

Install the preview

RC5.13 is a fresh-install evaluation preview for Apple Silicon macOS, x86-64 Linux and x86-64 Windows. Intel Macs are unsupported in RC5.13. Use a new isolated collection and empty destination with synthetic or disposable capabilities.

On an Apple Silicon Mac with Homebrew installed: 

brew install --cask kapital-labs/tap/kitrove
kitrove --version

This installs the latest reviewed preview, currently RC5.13. The shorter package name does not make it a stable release. Homebrew checks the pinned archive checksum; you trust Homebrew and the reviewed tap to select it. Installation does not initialize a collection or change your agent tools. Keep quarantine and Gatekeeper enabled.

Upgrade with Homebrew

Already using the kitrove cask from the Kapital Labs tap?

brew update
brew upgrade --cask kapital-labs/tap/kitrove
kitrove --version

Run brew update first. A stale copy of the tap can make Homebrew report that the latest version is already installed. The Kitrove upgrade replaces the executable and preserves your collection and local state. For the older cask names, see Existing installations.

Download RC5.13 and read its versioned release notes. Verify before running a manual download on macOS, Linux or Windows: follow the versioned verification and staging guide with an independently trusted or reviewed-source-built verifier. Match the exact tag, source commit and signer workflow; checksums alone are not provenance. A downloaded installer cannot authenticate its own first execution. Do not pipe downloads into a shell or PowerShell, remove quarantine, or disable Gatekeeper.

Older Linux package channels · RC4.2 only

APT/DNF still distribute RC4.2 and do not install RC5.13. The RC4.2 WinGet submission is not an RC5.13 install path. No Chocolatey package is published. These channels were not updated by RC5.13.

Linux x86-64 users can choose Ubuntu / APT or Fedora / DNF. These are RC4.2 package instructions, not RC5.13 installation or upgrade instructions. Authenticate a download before its first execution.

Set up your first computer

kitrove init
  1. Choose Set up my first computer.
  2. Choose a collection folder. Kitrove suggests ~/Kitrove and asks for a name for this computer. Review the collection and machine-local state locations before confirming creation.
  3. Enter previews recommended skills without writing them. Use v for the full inventory, 1,4,7 for only those entries, or all,-3,-8 (also -3,-8) for everything except entries 3 and 8. Review source tools and scopes as well as names; the same directory may appear through multiple tools.
  4. Review fidelity and loss warnings. Enter or y approves only the displayed ready set after a nonempty preview. Use r for individual review: Enter/y accepts the shown plan, n skips, and r renames before a new preview. Original source files stay in place.
  5. Select Choose skills to add to your AI tools, pick destinations, then review and confirm the separate application plan.

If repeated names leave nothing ready to collect, choose a numbered source tool to preview its copies with your exclusions still applied. You can also type from codex, from claude, from pi or from opencode. For example, from codex,-13,-20 excludes those original inventory numbers. Existing collection names and duplicates within one tool still need an explicit choice or individual review.

The preview shows skipped-item counts by reason. Press d for all details. Ready plans retain full source, fidelity and loss information. An empty preview offers no adoption approval and never reports zero-item success. Enter or s chooses again using the same scan; s also works after a nonempty preview.

Closed menus accept a single displayed key without Enter. Selection expressions, paths, names and URLs remain text prompts: type the value and press Enter. An Enter left over from an earlier prompt cannot approve a later preview. Apply and sync keep separate confirmations; Enter skips those writes. Type q to stop. Bulk adoption is sequential: a stale source, changed collection, pending recovery or failed commit stops later items. Completed items remain and are reported; setup is not one all-or-nothing transaction.

See the quick collection guide for omitted items, ambiguous names and exact confirmation semantics.

Your collection and local state are separate. On macOS, the default state folder is ~/Library/Application Support/kitrove. Setup shows both paths and does not edit your shell profile.

Return when you want to change something

kitrove configure

Select your existing collection to collect more skills, apply another selection, sync, or import selected items. To choose a non-default collection: 

kitrove configure --environment /absolute/path/to/collection

Already have an existing setup? kitrove init now checks it before offering to continue. It does not delete or recreate your collection or local state. Incomplete, unsafe or in-use state stops for inspection rather than automatic repair.

Choose Add skills from this computer to collect, Choose skills to add to your AI tools to preview local application, Share this collection with another computer to sync, or Copy selected items from another collection for a one-time import. Finish for now leaves setup.

Questions and the input marker are cyan in recognized interactive terminals. Results and no-write previews have separate labels and indentation. Set NO_COLOR for plain text; unrecognized terminals also stay plain. Labels and confirmations are the same.

Nothing starts syncing in the background. You choose a backend for each operation, review the plan, and confirm it.

Bring your collection to a second computer

On the first computer, open Configure and choose Share this collection with another computer. Use an existing filesystem/shared directory or Git repository. Paste the repository URL: https://... selects HTTPS and ssh://... selects SSH. A URL without its scheme asks which connection to use. SSH also asks for an absolute path to an existing known-hosts file; it does not learn host keys or start an agent. Setup does not create a remote repository, inspect the current project's remotes or import Git/SSH configuration. Create and authorize a repository separately. When sharing, type c at the URL prompt for instructions to create an empty private repository on your Git host, then paste its clone URL. HTTPS authentication asks for a username and a hidden access token.

This must be a Kitrove snapshot backend, not a regular checkout of skill files. An empty existing backend can receive the first approved publication. Review changes on both sides: full sync is bidirectional.

Install Kitrove on the second computer and run kitrove init. Choose the route that fits:

  • Connect a second computer to the whole collection. Create a new local identity and review full sync. Your agent files stay untouched until you choose Apply.
  • Combine this computer's skills with an existing collection. Connect an empty collection first to establish shared history. Then collect this computer's skills and review publishing the additions.
  • Import specific items. Choose assets or packs for a one-time import. Packs include their required members. This preserves unrelated local items and does not change the remote.

Two independently populated collections without shared history cannot full-sync automatically. Use selective import for chosen items. Do not delete local state to force a connection.

Conflicting content under the same identity stops the operation for review. RC5.13 does not choose an automatic winner or create a keep-both rewrite.

Inspect skills and choose by name

kitrove scan
kitrove scan --harness claude --scope user

In a terminal, the scan starts with a summary. Press a displayed number to browse skills in pages, d for diagnostics, or Enter to finish. The inventory is read-only. 

kitrove adopt humanizer --harness claude --scope user

The adoption command is an example for a uniquely named skill called humanizer. Replace it with a name from your scan. Ambiguous names need a narrower source or scope, or the exact observation ID from kitrove scan --verbose.

Scanning does not change files. Adoption still captures fresh content and requires a confirmed plan. For automation, use kitrove scan --json; bare Init and Configure require a terminal.

Know the boundaries

  • Collection sync excludes credentials, trust decisions, machine paths, local bindings, and deployment receipts. Install and authorize each agent tool on each computer.
  • Kitrove reports transfer fidelity. A successful import does not mean identical behavior in another tool.
  • Executable capabilities need separate local trust. Setup does not grant it or install prerequisites. Pi and OpenCode may ask for an independently trusted local binary for a bounded version check.
  • Kitrove refuses unmanaged destination conflicts instead of overwriting existing files.
  • Keep RC5.13 collections separate from older previews. RC4.2 cannot read authored packs. Do not downgrade a collection or treat binary rollback as data recovery.

RC5.13 remains a prerelease. Its published artifacts passed independent inventory, provenance, notice-byte and native Mac image verification; those checks did not install or execute the downloaded products. Prior bounded source-built Mac/Linux tests covered skill and authored-pack transfer, updates, conflict refusal and unmanaged-file protection. They are not RC5.13 production-artifact fresh-install acceptance, clean-Mac online/offline first launch, all capability types, live agent-tool execution, Git-provider acceptance or concurrent sync.

RC5.13 includes exact agent plan/approval workflows, locally authored packs and explicit partial-fidelity warnings for native-only skill fields. These features are not in the older RC4.2 package channels. Cloud-provider sync is roadmap work, not an available feature.

Existing installations

These instructions assume a fresh install. RC5.13 is not a supported in-place upgrade from RC4.2; no rollback-compatible predecessor is declared. Binary rollback does not roll back collection data.

The retained Homebrew tokens kitrove-rc (RC4.2) and kitrove-rc@5.5 (RC5.5) are not automatically renamed. The new kitrove cask refuses both installed tokens and an occupied executable. Check ownership and recovery needs before replacing an installation. Do not force an overwrite, delete state, use --zap, or use the standalone installer on Homebrew-managed files. Normal cask removal preserves collections and local state.
