## Audience and premise

Address a developer who uses more than one coding tool and has collected useful
skills in several places. Explain how they can choose what to keep, preview use
in another supported tool and understand the differences before changing files.
Lead with one user journey, not the release count, implementation language or a
catalog of every capability type.

The saved founder direction describes enjoying new harnesses while accumulating
uneven skills and configuration. Do not expand that into invented incidents,
employer examples, competitor usage or claims that Brandon tested a product.

## Strongest objection

"My tools already read SKILL.md and shared folders. Why do I need this?"

Answer with the managed collection workflow and its limits. Basic reuse may need
no new copy. Kitrove is a fit when a user wants retained native content, explicit
compatibility, owned placements and a way to review later changes. Existing
installers and declarative configuration tools are credible alternatives.

## Blog structure

1. The saved-skills problem across tools, using a concrete file workflow.
2. What collect, plan and apply mean, including an already-current item.
3. What a shared folder solves and where managed lifecycle matters.
4. Credit the closest alternatives, using the dated research instead of a
   superiority table or an unsupported list of missing features.
5. Describe the evaluation preview and ask for feedback from an isolated journey.

The companion LinkedIn post should stand on that mechanism and objection, then
point to the approved walkthrough. It should not repeat the whole blog.
