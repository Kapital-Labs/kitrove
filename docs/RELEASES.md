# Release Packaging

Kitrove release archives and installers are generated by the pinned `dist` 0.32.0 configuration.
Ordinary pushes and pull requests never run the release workflow. Only a pushed semantic-version tag
starts the four-platform build matrix.

The repository must protect `v*` tags and the `release` GitHub environment from unreviewed use. The
workflow additionally rejects non-SemVer tag names and commits that are not already ancestors of
`main`. Its write-capable publication job runs only inside that environment.

## Release artifacts

The Phase 6 packaging configuration produces separate native `kitrove` and
`kitrove-installer` archives for Apple Silicon macOS, Intel macOS, x86-64 Linux and
x86-64 Windows: eight binary archives total. Each product also has its own generated
shell and PowerShell convenience scripts. The inventory includes one source archive,
per-archive SHA-256 files and a combined checksum file. Packaging integration remains
under review; this configuration is not evidence that a release is published or that
the full installer/upgrade workflow has passed cross-platform acceptance.

Each platform archive contains `kitrove-release.json`. After `dist` builds an archive, the release
job replaces a checked-in empty placeholder with canonical metadata generated by the shared Rust
release policy. Application metadata binds the tag version, target, executable SHA-256, application-state
schema, lifecycle-lock protocol, and explicitly reviewed rollback-compatible predecessors. The job
then rebuilds and revalidates the archive and regenerates its adjacent checksum before any
attestation, scratch upload, combined checksum, or publication step. Edit
`release/application-compatibility.json` only as a reviewed release-policy change.
Installer metadata instead contains the exact `artifact_kind: "installer"`, executable
name, version, target and executable digest; it makes no application compatibility
claims. The two manifest formats and authentication roles are not interchangeable.
Each local archive receives its own single-subject attestation.

Every third-party GitHub Action is pinned to a full reviewed commit. Public-repository releases use
GitHub's Sigstore-backed artifact attestations for platform archives, installers, the source archive,
and global checksum controls. These attestations prove which workflow produced an artifact; they are
not Apple notarization or Windows Authenticode signing. Native signing preparation is now
implemented separately; hosted provisioning and real platform acceptance remain required
before Phase 6 is complete. See [platform signing](RELEASE-SIGNING.md).

## Prepare a release

1. Set the workspace version to the intended semantic version and update `CHANGELOG.md`.
2. Run the full stable and Rust 1.85 validation locally. The tag workflow repeats canonical stable
   validation and an MSRV workspace check against the exact tagged commit before packaging.
3. Run `cargo xtask governance`, then run `dist plan` with the pinned 0.32.0 binary and inspect every
   planned target, archive, installer, and checksum. The checked-in workflow deliberately preserves
   repository-specific verification beyond dist's generated baseline.
4. Build both local platform archives with `dist build --artifacts=local --target=<host target>`, run
   `cargo xtask prepare-platform-release` using the target, tag, reviewed compatibility catalog,
   and cargo-dist build manifest for each archive, then smoke-test both packaged binaries.
   The historical command name also accepts the exact installer archive catalog; its
   compatibility argument is used only for application archives. Preserve the JSON output
   of the actual `dist build`, not `dist plan` or `dist manifest`: only the build output
   contains computed checksum authority. Preparation updates
   the archive, adjacent checksum, and cargo-dist's checksum authority as one verified handoff so
   generated installers bind the final archive. The global build also hardens cargo-dist's
   PowerShell installer with the verified final Windows archive digest and mandatory verification
   before extraction. The tag workflow requires signed preparation and fails closed until
   separately approved hosted provisioning is activated. Unsigned local development packaging
   may use `prepare-application-release`; that is not releasable output.
5. Commit the release metadata, create the exact `v<version>` tag, and push that tag only after the
   release commit is reviewed.

The hardened workflow creates a draft GitHub release only after every selected platform build and
the global installer/checksum job succeed. It publishes that draft only after the complete upload
succeeds, so partial releases are not announced.

Before scratch upload and again before publication, the release jobs require the exact eight binary
archives and one source archive and inspect them without extracting them. Verification reads every
payload through one no-follow, identity-stable handle; bounds compressed and expanded size, entry
count, individual member size, and path length; rejects corruption, traversal, absolute and
drive-qualified paths, cross-platform name collisions, links, special files, unsafe TAR permissions,
encryption, unsupported compression, and unrecognized release artifacts; and requires binary
archives to contain the exact documented file set. The source archive must contain one versioned
Kitrove root. ZIP central-directory bounds and TAR decompression and extended metadata are checked
before the format parser can allocate from them. The final publication set is copied from the
verified open handles into a new private staging directory; control manifests and the mutable source
paths are not published. Archive SHA-256 digests are computed while those same handles are staged;
each adjacent checksum must contain its one exact archive mapping, and the combined checksum must
contain exactly the nine staged archive mappings with no missing, extra, or duplicate names. Any
refusal stops the release before publication.

## Verify a downloaded release

The selected public release authority is `Kapital-Labs/kitrove` (repository ID
`1360443188`, organization ID `320223113`). The offline verifier pins both IDs and
the exact repository/owner URIs; the private development repository is not accepted.
Renaming, transferring or recreating the public repository requires a reviewed policy
update. Creating the empty public repository did not publish source or release artifacts.

Verify the archive against its adjacent `.sha256` file before extracting it. For a public GitHub
release, a platform archive can also be checked against its build provenance:

```text
gh attestation verify <platform-archive> \
  --repo Kapital-Labs/kitrove \
  --signer-workflow Kapital-Labs/kitrove/.github/workflows/release.yml \
  --source-ref refs/tags/vX.Y.Z \
  --source-digest <release-commit-sha>
```

Verify an installer or source archive with the same command before trusting it, substituting that
artifact's filename. Resolve the intended tag independently and require its commit to equal
`<release-commit-sha>` before verification. The combined checksum control is also attested by the
release workflow. Repository-only verification is insufficient because it does not constrain which
workflow or source ref produced the attestation.

Kitrove does not self-update. ADR-0040 makes the verified platform archive authoritative for the
application upgrade workflow and requires a verified, offline prior-version rollback kit before
replacement. The generated installers remain convenience controls until cross-platform release tests
prove strict archive verification and prior-binary preservation or restoration on every failure path.
Do not pipe an installer directly from the network.

The library now also authenticates structurally inspected installer archives through
the same offline signature and exact-identity policy. Its installer result is distinct
from application replacement authority and retains the exact inspected bytes without
writing or executing them. This supports a future trusted bootstrap consumer; it does
not make a downloaded verifier trustworthy by verifying itself. Acquisition,
safe executable staging, and real public-release acceptance
remain required before a supported bootstrap can be advertised.

Exact JSONL-to-single-bundle handoff is now implemented by the read-only
`select-application-bundle` and `select-installer-bundle` commands in an independently
trusted or reviewed-source-built installer. They authenticate candidates under the
fixed release policy and reject zero/multiple matches and malformed collections.
See [INSTALLER.md](INSTALLER.md) for bounds and the local verification sequence.
